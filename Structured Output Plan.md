# Structured Output Plan

## Executive Summary

This plan converts the multi-agent RAG researcher from producing **Markdown reports** to producing a **validated JSON structured document** as its canonical output. The document is an intermediate representation that a separate document-generation project can render into PDF, HTML, EPUB, or other formats. The LLM agents continue to do what they do best — produce facts, reasoning, and source linkages — but instead of a Markdown stream destined for a Markdown file, they produce a schema-bound JSON document.

The document-generation pipeline (Jinja2 → WeasyPrint or Playwright → PDF) is explicitly **out of scope** for this work. It will be built as a standalone project that consumes the same JSON output from this project (and potentially from other applications).

---

## 1. Current State

### 1.1 Output Chain

```
Writer agent (LLM)
    ↓  produces Markdown string
Orchestrator assembly (deterministic)
    ↓  renumbers [D#]/[W#] keys → [n], drops invented keys
    ↓  appends "## References\n\n{formatted refs}"
deep_research() returns {"final_answer": str, "state": dict}
    ↓
save_report(content=final_answer) — memory/save_report.py
    ↓  wraps in: # Research Report, query, date, session, ---,
    ↓  ## Executive Summary, ---, footer
    ↓  writes {query}_{timestamp}.md to reports/
```

### 1.2 What the Writer Agents Produce Today

| Agent | Output format | Structure |
|-------|--------------|-----------|
| `writer_agent()` | Full-report Markdown | `## Report Outline`, then `## {Section}` blocks |
| `write_section()` | One `## Section Heading` block | Prose with `[D#]/[W#]` inline citation keys |
| `write_synthesis()` | One `## Synthesis` block | Prose connecting named sections, same citation keys |
| Executive summary | Prose paragraph only | No heading, no citations |

### 1.3 What the Orchestrator Adds on Top

The orchestrator's stage-5 assembly does deterministic post-processing:
- Strips invented citation keys (keys cited but absent from registry)
- Renumbers `[D#]/[W#]` → `[1]/[2]/…/[N]`
- Drops unresolved bare `[n]` markers
- Appends a `## References` section with numbered entries from `format_references()`

### 1.4 What `save_report` Adds on Top

- Wraps content under `# Research Report` and `## Executive Summary`
- Adds `**Query:**`, `**Date:**`, `**Session ID:**`, `**Generated:**` metadata
- Optionally inlines or side-files the evidence dump
- Adds `## Verification Output` block (only if different from body)
- Footer: "*This report was automatically generated…*"

## 2. Target Architecture

```
Writer agents (LLM)
    ↓  produce block-level JSON (not Markdown)
Orchestrator assembly (deterministic)
    ↓  validates schema
    ↓  deduplicates / reconciles citation registry
    ↓  computes citation density & metadata
deep_research() returns {"report": ReportModel, "state": dict}
    ↓
save_report(report) writes {query}_{timestamp}.json to reports/
    ↓
[separate project] document-generator/
    ↓  Jinja2 template → HTML → WeasyPrint → PDF
    ↓  or React → server-side HTML → Playwright → PDF
    ↓  or Pandoc JSON → DOCX / EPUB
```

## 3. Document Model (JSON Schema)

### 3.1 Top-Level Shape

```json
{
  "schema_version": "1.0",
  "report": {
    "metadata": { ... },
    "executive_summary": [ ... ],
    "sections": [ ... ],
    "sources": [ ... ]
  },
  "quality": { ... }
}
```

### 3.2 Metadata

```json
"metadata": {
  "title": "Diffusion Language Models: A Comprehensive Survey",
  "subtitle": null,
  "query": "Prepare a comprehensive report about diffusion models and how they relate to LLMs",
  "session_id": "uuid...",
  "generated_at": "2026-08-25T18:06:32Z",
  "author": "Research Assistant",
  "report_type": "deep_research"
}
```

The **title** and **subtitle** will be generated by the LLM (new prompt addition). The title should describe the topic, not mirror the query.

### 3.3 Executive Summary

```json
"executive_summary": [
  "Finding one: The first paragraph of synthesized findings..."
]
```

A list of prose paragraphs (not a single string) so the renderer can apply paragraph-level styling.

### 3.4 Sections

Each section corresponds to one `write_section()` or `write_synthesis()` call:

```json
{
  "id": "market-landscape",
  "heading": "Market landscape",
  "blocks": [
    {
      "type": "paragraph",
      "spans": [
        {
          "text": "Grid-scale deployment rose sharply in several major electricity markets.",
          "citations": ["1"]
        }
      ]
    },
    {
      "type": "ordered_list",
      "items": [
        {
          "text": "First item",
          "spans": [
            {"text": "with ", "citations": []},
            {"text": "inline ", "citations": ["3"]},
            {"text": "citations", "citations": ["1", "2"]}
          ]
        }
      ]
    }
  ]
}
```

### 3.5 Block Types

| Type | Purpose | Inline Spans | Sub-items |
|------|---------|:-----------:|:---------:|
| `heading` | `## Section` or `### Subsection` | Yes | No (level from `level` field) |
| `paragraph` | Body prose | Yes | No |
| `ordered_list` | Numbered list | Yes | No (items are text+spans) |
| `unordered_list` | Bullet list | Yes | No |
| `callout` | Note/warning/info box | Yes | No |
| `comparison_table` | Row/column data | Yes | Rows array |
| `code_block` | Code / formula | No (single `language` + `text`) | No |
| `page_break` | Force a new page | No | No |
| `citation_note` | "The available evidence does not cover X" | Yes | No |

**Inline spans** are a list of `{text, citations?}` pairs. This is what makes citations first-class: the renderer can style, underline, or suppress citations; the data model knows which words are cited.

### 3.6 Sources (CSL-JSON Compatible)

```json
"sources": [
  {
    "id": "source-1",
    "type": "report",
    "title": "Batteries and Secure Energy Transitions",
    "author": [{ "literal": "International Energy Agency" }],
    "issued": { "date-parts": [[2025]] },
    "URL": "https://www.iea.org/reports/batteries-and-secure-energy-transitions",
    "publisher": "International Energy Agency",
    "citation_key": "D1"
  }
]
```

This is **CSL-JSON** for the bibliographic fields that matter, extended with a `citation_key` that bridges to the internal `[D#]/[W#]` registry used during drafting. The renderer maps `citation_key` to the CSL JSON key for inline citation generation.

### 3.7 Quality / Provenance

```json
"quality": {
  "citation_density": {
    "overall": 4.2,
    "per_section": { "Definition & Background": 5.1, ... }
  },
  "verification": {
    "confidence": "high",
    "coverage": "comprehensive",
    "gaps": []
  },
  "sources_count": {
    "documents": 12,
    "web": 8
  },
  "total_words": 4850
}
```

## 4. Schema Definition

Use **Pydantic v2 models** (already a dependency via `verifier_agent.py`) for the schema. Define in a new module:

**File**: `models/report_schema.py`

```python
from pydantic import BaseModel, Field
from typing import Literal, Optional
from datetime import datetime
from enum import Enum

class BlockType(str, Enum):
    heading = "heading"
    paragraph = "paragraph"
    ordered_list = "ordered_list"
    unordered_list = "unordered_list"
    callout = "callout"
    comparison_table = "comparison_table"
    code_block = "code_block"
    page_break = "page_break"
    citation_note = "citation_note"

class Span(BaseModel):
    text: str
    citations: list[str] = Field(default_factory=list)

class ReportBlock(BaseModel):
    type: BlockType
    # Shared
    text: str = ""            # for code_block, page_break, single-span blocks
    spans: list[Span] = []    # for prose blocks
    citations: list[str] = [] # shorthand for spans (unless spans is set)

    # Heading-specific
    level: int = 2

    # List-specific
    items: list[Span] = []

    # Table-specific
    caption: str = ""
    columns: list[str] = []
    rows: list[list[Span]] = []

    # Callout-specific
    callout_type: Literal["note", "warning", "info"] = "note"
    callout_title: str = ""

    # Code block
    language: str = ""

class Section(BaseModel):
    id: str = ""                  # slug or auto-generated
    heading: str
    blocks: list[ReportBlock] = []

class Source(BaseModel):
    id: str                       # stable UUID or "source-1"
    type: str = "web"             # CSL item-type: report, article, webpage, etc.
    title: str = ""
    author: list[dict] = []       # CSL author: [{"literal": "..."}] or [{"family": "...", "given": "..."}]
    issued: dict = {}             # CSL issued: {"date-parts": [[2025]]}
    URL: str = ""
    publisher: str = ""
    DOI: str = ""
    citation_key: str = ""        # "D3" or "W7" — bridges to internal registry
    accessed: str = ""            # date string

class Metadata(BaseModel):
    title: str
    subtitle: str = ""
    query: str
    session_id: str
    generated_at: str             # ISO 8601
    author: str = "Research Assistant"
    report_type: Literal["standard", "deep_research"] = "deep_research"

class QualityMetrics(BaseModel):
    citation_density: dict = {}
    verification: dict = {}
    sources_count: dict = {}
    total_words: int = 0

class Report(BaseModel):
    metadata: Metadata
    executive_summary: list[str] = []
    sections: list[Section] = []
    sources: list[Source] = []

class ResearchReport(BaseModel):
    schema_version: str = "1.0"
    report: Report
    quality: QualityMetrics
```

### 4.1 JSON Schema for Downstream Validation

Also export a `to_json_schema()` that produces a JSON Schema document suitable for:
- Validating the output in the document-generation project
- IDE auto-completion
- Type-checking in JS/TS consumers

## 5. Agent Changes

### 5.1 Writer Agent — New Prompt for JSON Output

**File**: `worker_agents/writer_agent.py`

Add a new mode/flag `output_format="json"` (default stays `"markdown"` for backward compatibility during migration).

The writer prompt must:
1. Accept a **block vocabulary** (the set of allowed `type` values)
2. Accept a **citations list** (the available `citation_key` values)
3. Produce a JSON object shaped like `Section` or `ReportBlock`

#### Example writer prompt

```
You are writing ONE section of a deep-research report.

Output ONLY valid JSON matching this schema:
{
  "id": "<slug>",
  "heading": "<section title>",
  "blocks": [
    {"type": "paragraph", "spans": [
      {"text": "Prose here.", "citations": ["D1", "W3"]}
    ]},
    {"type": "heading", "level": 3, "text": "Subsection"},
    {"type": "unordered_list", "items": [
      {"text": "List item", "citations": ["D2"]}
    ]}
  ]
}

RULES:
- Every factual sentence must carry at least one citation from: [D1, D2, D3, W1, W2]
- Cite at the span level (within the text, not on the whole block)
- Use only the block types above
- Do NOT include Markdown formatting, ## headings, or code fences
- Prose sentences without supporting evidence should be omitted or marked as synthesis
- Use "paragraph" for body text, "heading" (level 2 or 3) for section headers
- Use "unordered_list" or "ordered_list" for lists
- Use "comparison_table" only when comparing 2+ items across shared dimensions
- Include a "citation_note" block at the end if the evidence does not cover an expected subtopic:
  {"type": "citation_note", "text": "The available evidence does not cover X"}
```

### 5.2 Writer Agent — Backward-Compatible Path

Keep the existing Markdown path as default. Add:

```python
def writer_agent(..., output_format: str = "markdown") -> dict | str:
    """Return str (Markdown) or dict (structured) depending on output_format."""
```

This lets us migrate incrementally: test the JSON path on a few queries, validate output quality, then flip the default.

### 5.3 Verification of JSON Output

The writer's structured output should be validated immediately after generation:

```python
response = run_model(...)
raw = response.output_text
try:
    parsed = Section.model_validate(json.loads(raw))
except Exception:
    # Fallback: try to extract JSON from ```json ... ``` fence
    # If that also fails, log warning and return empty Section
    ...
```

### 5.4 Executive Summary — Also Structured

Add a new call in the orchestrator (stage 5) that asks the LLM to produce the exec summary as a list of paragraph strings:

```python
EXEC_SUMMARY_JSON_INSTRUCTIONS = """
You are writing the executive summary of a finished deep-research report.

Write 150-250 words split into 2-4 paragraphs of connected prose.
Return ONLY a JSON array of paragraph strings.

Example:
["Paragraph one of the summary...", "Paragraph two..."]

Do not include any heading, preamble, or metadata.
Do not use citations.
"""
```

### 5.5 Title & Subtitle Generation

Add a step in the orchestrator (or to the writer's instructions) to produce a title and subtitle. The decomposer can suggest a title based on the query. If not, the writer generates one as part of the first section or as a separate LLM call.

## 6. Orchestrator Changes

### 6.1 `deep_research()` — New Return Shape

```python
def deep_research(...) -> dict:
    """Returns {"report": ResearchReport, "state": dict, "stats": dict}

    The "report" field is a validated ResearchReport model (Pydantic).
    The "state" field is preserved for backward compat with save_report,
    but downstream consumers should read from "report".
    """
```

### 6.2 Assembly Stage Restructuring

The current assembly stage does Markdown post-processing (key stripping, renumbering, appending References). Replace with JSON-stage equivalents:

| Current Step | New Equivalent |
|---|---|
| `_strip_invented_keys()` | `ReportBlock` validation — unknown citation keys flagged in `quality.verification.unresolvable_citations` |
| `_renumber_inline_keys()` | CITATION BROADCAST: replace every internal `citation_key` (D1, W3) in spans with the **rendered number** (1, 2, …) using the resolved registry |
| `_drop_unresolved_numbers()` | Drop bare-number citations during JSON validation (model-level, deterministic) |
| `format_references()` → Markdown | `format_references()` → `list[Source]` with CSL-JSON fields, `citation_key` bridging |
| Append `## References` block | Merge references into `report.sources` array |

### 6.3 Citation Key Renumbering — New Algorithm

The current algorithm renumbers `[D#]/[W#]` text patterns. The new one works on the structured data:

```python
def _renumber_json_citations(
    report: Report, registry: dict, cited_keys: list[str]
) -> Report:
    """Replace every citation_key reference in spans with its [n] number."""
    key_to_number = _key_number_map(cited_keys, registry)
    for section in report.sections:
        for block in section.blocks:
            for span in block.spans:
                span.citations = [
                    str(key_to_number[k]) for k in span.citations if k in key_to_number
                ]
    return report
```

### 6.4 State Envelope — What `state` Should Carry

The `state` dict (which `save_report` currently consumes) needs a **JSON report** alongside the legacy text fields during the migration window. After migration, `state` can be slimmed:

```python
state = {
    "report_json": json.dumps(report.model_dump()),  # NEW
    "evidence_json": ...,   # keep for evidence dump
    "verification": ...,     # keep for backward compat
    "verification_status": ...,
    "sections": ...,
    "critic": ...,
}
```

The evidence dump (`.evidence.md`) remains alongside the JSON, unchanged. The side-file is independent of the report format.

## 8. New Helper Functions

### 8.1 Registry → Sources Mapping

**File**: `memory/helpers.py` (new section)

```python
def registry_to_sources(
    registry: dict,
    cited_keys: list[str],
) -> list[dict]:
    """Convert the citation registry into CSL-JSON compatible source records.
    
    Only keys present in `cited_keys` are included (uncited sources are excluded
    from the output unless `include_uncited=True`).
    """
```

Each doc-chunk registry entry maps to a `Source` with `type="report"` or `type="webpage"`. Multiple chunks from the same document should be **deduplicated** at the source level (one source record per unique URL/title, with `citation_key` being a list or the primary key's value).

### 8.2 Section Markdown → Structured Block Conversion

For incremental migration, provide a parser that converts a writer's Markdown section into structured blocks. This can be a `Section.from_markdown(text)` classmethod:

```python
@classmethod
def from_markdown(cls, text: str, registry: dict) -> "Section":
    """Parse a Markdown section into structured blocks.
    
    Use for migration and testing. Not part of the primary pipeline.
    """
```

This is a convenience for converting **existing reports** to the new format for validation, not for the live pipeline.

## 11. Risks & Mitigations

| Risk | Likelihood | Impact | Mitigation |
|------|-----------|--------|-----------|
| LLM produces malformed JSON | High | Medium | Post-parse Pydantic validation; fallback to empty section with warning |
| LLM ignores citation span granularity | Medium | Medium | Prompt examples showing inline `spans` with per-sentence citations; validation rejects blocks where all text is in one span with all citations |
| Title/subtitle quality is poor | Medium | Low | Extract from query as fallback; title is cosmetic |
| CSL-JSON mapping is lossy | Low | Medium | Registry already has all metadata; mapping is deterministic, no LLM involved |
| Backward compat breaks gradio UI | Medium | Medium | Keep `state` dict populated with legacy fields during migration |
| Per-span citation density hurts LLM quality | Low | Low | Allow `citations: []` on synthesis/transition spans |

## 12. Document Generation Project (Separate, Out of Scope)

The consumer of this JSON will be a standalone project called `document-generator` (or similar). Its responsibilities:

1. **Validate** the incoming JSON against the schema (JSON Schema or Pydantic)
2. **Render** to HTML via Jinja2 template
3. **Apply** print CSS (page margins, headers/footers, page numbers)
4. **Export** to PDF via WeasyPrint or Playwright
5. **Export** to other formats: EPUB, DOCX (via Pandoc), HTML standalone
6. **Validate** output: text extraction, glyph coverage, link integrity

Key design principles for the consumer:
- **Templated**: CSS and HTML template are separate from the renderer logic
- **Configurable**: page size, margins, fonts, header/footer content
- **Citation-aware**: inline superscripts, numbered reference list, CSL style
- **Unicode-safe**: UTF-8 throughout, font fallback stack

The consumer project consumes the JSON from this project's `reports/` directory (or an API). It is agnostic to how the JSON was produced.

## 15. Open Decisions

| Decision | Options | Recommendation | Rationale |
|----------|---------|----------------|-----------|
| Citation granularity | Per-sentence spans vs. per-block citations | **Per-sentence spans** | Enables renderer to style/hover individual claims; matches PDF Gen recommendation |
| Source deduplication | One record per chunk vs. one per document | **One per document** (de-duplicated in `registry_to_sources`) | Prevents the bibliography from listing the same paper 20 times |
| Title generation | Decomposer suggests title vs. dedicated LLM call | **Decomposer suggests** (use as-is if good, else writer generates) | Saves one LLM call; decomposer already understands the query |
| Executive summary format | Single string vs. list of paragraphs | **List of paragraphs** | Consistent with block model; renderer can apply paragraph styling |
| Migration default | JSON always vs. keep Markdown default | **Default stays Markdown** until Phase 5 | Backward compatibility with tests and UI during migration |
| CSL-JSON adoption level | Full CSL-JSON vs. minimal extended format | **CSL-JSON core fields + `citation_key`** | Enough for citeproc-style rendering; avoids overloading the model with CSL complexity |
| Validation strictness | Hard-fail on invalid JSON vs. soft-fail with warning | **Soft-fail** — validate, drop bad blocks, log warning | LLM JSON is unreliable; hard-fail would crash the pipeline |
